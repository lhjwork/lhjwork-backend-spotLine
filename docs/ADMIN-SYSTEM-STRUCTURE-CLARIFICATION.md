# 🎯 Admin 시스템 구조 명확화 문서

## 📋 현재 시스템 구조 (정확한 이해)

### 🎭 데모 시스템 (업주 소개용)

- **스키마**: `DemoStore` (완전히 별도)
- **목적**: 업주에게 서비스를 소개할 때만 사용
- **데이터**: 현재 DB에 있는 모든 임시 데이터들
- **특징**:
  - 통계 수집 **없음**
  - `isDemoOnly: true` 플래그
  - 프론트엔드에서 "데모" 표시
- **API**: `/api/demo/*`

### 🏪 실제 운영 시스템 (Admin 관리)

- **스키마**: `Store` (실제 서비스용)
- **목적**: 실제 SpotLine 서비스 운영
- **데이터**: **현재 비어있음** (Admin이 등록해야 함)
- **특징**:
  - 완전한 통계 수집
  - 실제 추천 시스템 작동
  - 실제 사용자 데이터 수집
- **API**: `/api/stores/*`, `/api/experience`

## 🔧 Admin 시스템에서 관리해야 할 것들

### 1. 실제 매장 등록 (Store 스키마)

```json
{
  "name": "실제 카페명",
  "category": "cafe",
  "location": {
    "address": "실제 주소",
    "coordinates": [경도, 위도],
    "area": "강남역"
  },
  "qrCode": {
    "id": "real_cafe_001",  // 실제 QR 코드 ID
    "isActive": true
  },
  "shortDescription": "실제 매장 설명",
  "representativeImage": "실제 이미지 URL",
  "externalLinks": {
    "instagram": "실제 인스타그램",
    "website": "실제 웹사이트"
  },
  "isActive": true
}
```

### 2. 체험하기 설정 관리 (ExperienceConfig)

- 어떤 매장을 체험용으로 보여줄지 설정
- 랜덤/순차/고정 선택 방식 설정
- 체험 활성화/비활성화 관리

### 3. 실제 추천 관계 설정 (Recommendation)

- 실제 매장 간의 추천 관계 설정
- A 매장 → B, C, D 매장 추천 설정

### 4. 분석 데이터 관리 (Analytics)

- 실제 사용자 행동 데이터 분석
- 체험 데이터 vs 실제 사용 데이터 구분
- 매장별 방문 통계

## 🚨 중요: 현재 상태

### ✅ 올바르게 구현된 것들

1. **데모 시스템 완전 분리**: `DemoStore` 스키마로 별도 관리
2. **실제 운영 시스템 준비**: `Store` 스키마 준비 완료
3. **API 엔드포인트 분리**: `/api/demo/*` vs `/api/stores/*`
4. **통계 수집 구분**: 데모는 수집 안함, 실제는 수집함

### 📝 Admin이 해야 할 작업

1. **실제 매장 등록**: `Store` 스키마에 실제 운영할 매장들 등록
2. **QR 코드 발급**: 실제 매장용 QR 코드 ID 생성 및 관리
3. **추천 관계 설정**: 매장 간 추천 관계 설정
4. **체험 설정**: 어떤 매장을 체험용으로 노출할지 설정

## 🎯 Admin UI에서 구분해야 할 메뉴

### 1. 데모 관리 (읽기 전용)

```
📋 데모 매장 목록
├── 카페 데모 (demo_cafe_001)
├── 레스토랑 데모 (demo_restaurant_001)
├── 전시 데모 (demo_exhibition_001)
└── 호텔 데모 (demo_hotel_001)

⚠️ 데모 데이터는 수정하지 마세요
💡 이 데이터들은 업주 소개용입니다
```

### 2. 실제 매장 관리 (CRUD)

```
🏪 실제 매장 관리
├── ➕ 새 매장 등록
├── 📝 매장 정보 수정
├── 🔗 QR 코드 관리
└── 📊 매장 통계

현재 등록된 매장: 0개
⚠️ 실제 서비스를 위해 매장을 등록해주세요
```

### 3. 체험하기 설정

```
🎯 SpotLine 체험하기 설정
├── 체험 활성화/비활성화
├── 체험 방식 선택 (랜덤/순차/고정)
├── 체험 대상 매장 선택
└── 체험 통계 확인

⚠️ 실제 매장이 등록되어야 설정 가능합니다
```

### 4. 추천 시스템 관리

```
🔗 매장 추천 관계 설정
├── A 매장 → B, C, D 매장
├── 추천 가중치 설정
└── 추천 성과 분석

⚠️ 최소 2개 이상의 매장이 필요합니다
```

## 📊 데이터 흐름 구분

### 데모 흐름 (업주 소개용)

```
사용자 클릭 "데모 체험하기"
↓
/api/demo/experience
↓
DemoStore에서 랜덤 선택
↓
/api/demo/stores/{qrId}
↓
통계 수집 없음
```

### 실제 체험 흐름

```
사용자 클릭 "SpotLine 체험하기"
↓
/api/experience
↓
Store에서 관리자 설정에 따라 선택
↓
/api/stores/spotline/{qrId}
↓
Analytics에 통계 수집
```

### 실제 QR 스캔 흐름

```
사용자가 실제 QR 코드 스캔
↓
/api/stores/spotline/{qrId}
↓
Store에서 매장 정보 조회
↓
Recommendation에서 다음 매장 추천
↓
Analytics에 모든 행동 기록
```

## 🔄 Admin 개발 우선순위

### Phase 1: 기본 매장 관리

1. 실제 매장 등록 기능
2. QR 코드 생성 및 관리
3. 매장 정보 수정/삭제

### Phase 2: 체험 시스템 연동

1. 체험하기 설정 관리
2. 체험 대상 매장 선택
3. 체험 통계 확인

### Phase 3: 고급 기능

1. 매장 간 추천 관계 설정
2. 상세 분석 대시보드
3. 사용자 행동 분석

## ⚠️ 주의사항

1. **데모 데이터 건드리지 말기**: `DemoStore` 데이터는 업주 소개용이므로 수정 금지
2. **실제 데이터만 관리**: Admin에서는 `Store` 스키마의 실제 운영 데이터만 관리
3. **QR 코드 ID 중복 방지**: 데모용과 실제용 QR 코드 ID가 겹치지 않도록 주의
4. **통계 구분**: 데모 사용과 실제 사용 통계를 명확히 구분

## 🎯 최종 목표

- **데모**: 업주에게 "이런 서비스입니다" 보여주기
- **체험**: 사용자에게 "실제로 써보세요" 제공하기
- **운영**: 정식 서비스로 "실제 매장에서 사용하기"

각각이 완전히 분리되어 독립적으로 작동하는 구조입니다.
